## 2. 原型覆盖范围

### 老师

- 今日
- 学生
- 我的积累
- 任务陪伴进度
- 学生、记录和任务证据详情
- 返回企业微信与小优继续处理

### 店长

- 今日现场
- 学生
- 团队
- 任务
- 安全、服务异常、协作支持和关闭证据
- 返回企业微信让小优推进

### 老板

- 决策
- 经营
- 团队
- 小优
- 目标、执行回执、日报和主动联系真实状态
- 强证据新项目机会、验证边界和老板决策入口
- 返回企业微信告诉小优经营决定

## 3. 本轮视觉判断

- 产品名称统一为“小优工作台”，不显示技术底座名称。
- 首屏先显示角色真正需要处理的内容，不先显示指标总览。
- 事实、小优判断和执行回执分别用来源文案和状态标签表达。
- 老师侧不显示绩效树、工资、排名或团队比较。
- 店长侧不显示老师排名，使用“谁需要支持、为什么”组织团队页。
- 老板侧不把候选写成已完成，明确区分需决定、推进中、已送达和已核验。
- 底部导航固定为老师3项、店长4项、老板4项。
- 页面采用移动端三段结构：身份区、独立滚动内容区、稳定底部导航。
- 卡片圆角、字号、间距、状态色和触控尺寸遵守冻结设计系统。

## 4. 数据实现判断

可以直接使用现有真实来源：

- 学生和责任关系；
- 人员角色及状态；
- 任务和关闭证据；
- 老师服务记录和材料；
- 项目范围；
- 日报生成与发送状态；
- outbox发送结果；
- 目标和小优工作项。
- 项目机会的30天内部证据包与追加式候选事件。

正式V1开发需要补的只读投影：

- 每个源文件独立的新鲜度；
- 老师、店长、老板各自的 `WorkbenchProjection`；
- 唯一学生覆盖率；
- active/left/unknown人员状态聚合；
- 候选、已入队、已送达、已回复和已核验的统一展示状态；
- 学生、任务、记录按页面对象聚合。
- 老板专属 `project_opportunities` 投影和强证据诚实空状态。

以上都不产生第二套业务状态，不改变现有业务写入链路。

## 5. 原型中有意不做的内容

- 不展示生产真实数据；
- 不接入企业微信真实跳转；
- 不在H5创建、取消或完成任务；
- 不展示绩效、工资和内部规则；旧关键词经营机会已删除，只展示达到强证据门槛的新项目机会；
- 不在H5批准验证、创建试点或正式立项，相关决定返回企业微信交给小优执行；
- 不展示员工聊天原文和员工声音原文；
- 不展示续费、流失、招生等尚无权威账本的预测；
- 不验证生产接口性能；
- 不修改正式 `dashboard_http.py` 或 `dashboard_builder.py`。

## 6. 已完成的原型门禁

- 3个角色切换正常；
- 11个一级页面可访问；
- 老师3个、店长4个、老板4个底部导航准确；
- 360、390、430px无横向溢出；
- 1024px桌面预览保持430px移动工作台宽度；
- 底部导航与内容滚动区不重叠；
- 导航、角色按钮和主要操作文字无截断；
- 页面无卡片套卡片；
- 详情抽屉和返回企业微信示意交互正常；
- 控制台无页面脚本错误。

## 7. 本次评审只确认四件事

1. 老师首页是否确实应该先看到任务帮助和重点学生；
2. 店长首页是否确实应该先看到现场断点和协作事项；
3. 老板首页是否确实应该先看到需要决定的事项和小优执行回执；
4. 当前视觉是否符合“专业、安静、可信、愿意长期打开”的方向。

原型通过后，才进入正式开发。正式开发第一步是测试先行地建立只读 `WorkbenchProjection`，第二步才替换现有内嵌H5页面，最后使用三种真实角色签名链接进行canary验收。
