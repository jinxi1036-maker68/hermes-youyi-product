# 当前工作方式｜WM-004 Adaptive Evidence-First Project Method

> **机器权威：`knowledge/WORKING_METHOD.json`**  
> 本文件是当前工作方式的人类可读投影。

## 核心思想

我们不只让“小U产品”学习，也让“开发小U的方式”学习。

工作方式不是每个聊天窗口的个人习惯，而是项目资产。它可以改变，但必须有：

- 当前版本；
- 为什么改变；
- 旧方法哪里不够；
- 新方法解决什么；
- 是否被实际工作验证；
- 历史版本；
- 新窗口必须继承哪一版。

## 当前默认节奏

### 1. 先定位，不开工
读 Project Index → Freshness Gate → Current State → Active Work → Current Working Method。

### 2. 一次只解决当前阶段一个真实问题
先写清：
- 当前命题；
- blocker；
- non-goals；
- 需要什么证据；
- 什么情况必须 STOP。

### 3. 先分清谁负责
- Owner：经营/产品决策、最终真人验收、必要生产授权；
- ChatGPT：技术负责人、GitHub代码执行者、证据判断、路线控制；
- Codex：服务器检查、隔离验证、部署、回滚。

不默认让 Owner 当传话员，不把 GitHub 实现推给 Codex。

### 4. 先查根因，再改
复杂问题先画真实调用链/数据链/运行链。
区分：
- 模型判断问题；
- 业务权威问题；
- 代码问题；
- Runtime/部署问题；
- 工作流程本身的问题。

### 5. 最小、通用、可回滚
不为单个测试句写死；
不越过 Stage；
不把程序重新做成第二业务脑；
不顺手混入历史技术债。

### 6. 候选必须和稳定基线比较
必要时跑 A/B。
稳定基线也失败的，不算 candidate-only regression。

### 7. 服务器只验证和执行
Codex收到的是：
**背景 + 目标 + 必须结果 + 边界 + 证据 + STOP条件**。

它不自行重构 GitHub，也不替 ChatGPT做架构决定。

### 8. 生产失败后不盲重试
如果失败证明是结构问题：
**STOP → 找根因 → 新证据 → 再决定是否重试。**

### 9. 技术门禁之后才轮到真人业务验收
只有确实需要 Owner 实测时，明确告诉 Owner：

> **现在轮到你实测了。**

### 10. 工作完成必须同步知识
代码 merge 不是完整 Done。
重要状态发生变化后必须同步 Project Knowledge。

## 工作方式本身如何升级

发现“我们的做法”有问题时，不直接偷偷改习惯。

执行：

```text
发现流程问题
→ 判断是不是工作方法问题
→ 提出候选方法
→ 小范围验证
→ 比较速度/正确性/风险/返工
→ 接受或拒绝
→ 接受则升级 WM 版本
→ 写入 Method History
→ 新窗口自动继承
```

因此以后可以有 WM-005、WM-006……

但**版本越来越大不代表规则越来越多**。真正好的升级可能是删掉无价值步骤，让流程更短。

## 方法优化的目标

不是让流程越来越复杂，而是：

> **更少返工、更少重复解释、更少盲试、更少用户传话，同时保持更高正确性和生产安全。**
