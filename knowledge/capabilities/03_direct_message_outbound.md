# Stage 3｜Direct Message / Outbound

- Status: **FROZEN — Owner approved first slice**
- Stage: 3
- Work item: `WI-2026-09-stage3-direct-message-outbound-v2`

## 这一阶段只证明什么

让小U第一次具备正式、可审计、可验证的“把一条工作消息发给另一个人”的产品能力。

它不是“会聊天”。
它证明的是：

> 一个有权限的人明确要求小U联系某个合法对象时，小U能正确理解要求、找到唯一正确收件人、发出正确消息，并如实说明到底发到了哪一步。

## 建议的第一刀范围

先只做：

- 明确的人类指令；
- 1 对 1；
- 机构内部当前授权人员；
- 企业微信直发；
- 单条工作消息。

暂不纳入：

- 家长/外部客户；
- 群发/广播；
- AI自主找人；
- Agenda 自动追问；
- 任务催办；
- 学生资料写入；
- 人员组织变更。

## 权威与职责

### 模型负责

- 理解用户到底要联系谁、为什么联系；
- 判断是否应调用 Direct Message Tool；
- 形成消息正文；
- 缺事实时自然追问；
- 根据 Tool 真实回执向用户表达结果。

### Runtime/Core 负责

- 当前发送者可信身份；
- tenant；
- 权限；
- 收件人唯一解析与当前可达性；
- 渠道绑定；
- 幂等；
- 执行；
- 发送回执；
- 恢复与审计。

Runtime 不得根据关键词替模型决定“给谁发、为什么发、发什么”。

## 真值语义

必须区分：

- requested
- prepared
- queued
- API accepted / sent
- received（只有渠道真的能证明时）
- completed（业务完成，不等于消息发出）

绝不能：

- “准备好了”说成“已经发了”；
- “API 接收”说成“对方已经看了”；
- “消息发出”说成“对方已经完成工作”。

## 第一版 PASS 草案

1. 老板/有权限用户明确说“给某位老师发……”
2. 模型选择 outbound 能力。
3. 系统把姓名解析到唯一当前授权内部人员。
4. 同名/未知/离职/跨 tenant → 不发送。
5. 正确权限 → 只发一次。
6. 重试/恢复不能重复发送。
7. Tool 回执能证明实际执行状态。
8. 小U最终回复严格匹配真实发送状态。
9. 真实企业微信验收至少完成一次成功发送和一次阻断场景。
10. 不引入 Stage 8/9/10 的任务、追问或自主 Agenda 语义。
